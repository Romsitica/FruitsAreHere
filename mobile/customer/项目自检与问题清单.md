## 一、客户移动端：已修复的三个问题

### C01：首次进入订单详情后，已读订单又被标成未读

- 优先级：P2；状态：已修复。
- 位置：`mobile/customer/app.js` 的 `syncAlertUser`、`readOrder`、`recordOrders`。
- 复现：已经登录，直接打开一笔已确认订单的详情；详情先加载成功，应用的第一次订单轮询随后返回。
- 原因：详情清除提醒时只记录状态，没有初始化提醒所属账户。首次轮询认为账户变化，清空已读状态，又将同一订单标红。
- 修复：详情读取与轮询统一先同步提醒所属账户，再更新订单状态和未读集合。
- 验证：新增“首次打开已确认详情后首次轮询不重新标红”的回归测试；同时保留原有换号隔离、查看订单后不重复提醒的测试。

### C02：商户刚充值，客户端仍按旧余额拒绝下单

- 优先级：P2；状态：已修复。
- 位置：`mobile/customer/app.js` 的 `CtDetail.submit`。
- 复现：余额为零时打开商品页；商户为该会员充值；不刷新商品页，直接选择余额支付并预约。
- 原因：提交前使用缓存 `Auth.user.balanceCents` 判断余额。缓存尚未刷新，前端就拦截请求，即使服务器余额足够也无法下单。
- 修复：取消以缓存余额作为最终提交门槛，交由 `/api/orders` 在事务中检查实时余额。保留数量、库存范围、取货时间和重复点击校验，成功后刷新账户。
- 验证：专用测试会员以零余额打开商品页，服务器充值后原页面成功余额下单；扣款金额正确，取消后退款正确，重复取消被拒绝。
- 补充：页面上的余额数字仍是最近一次查询的快照，不代表实时推送。真正余额不足时后端继续返回业务错误，不会创建成功订单或扣库存。

### C03：商户刚发放积分，客户端仍按旧积分拒绝兑换

- 优先级：P2；状态：已修复。
- 位置：`mobile/customer/app.js` 的 `CtPoints.ask`、`confirm`。
- 复现：积分为零时打开积分页；商户完成该会员的订单并发放积分；不离开积分页，直接点击兑换。
- 原因：打开确认弹层前用缓存积分拦截，而订单状态轮询不会更新积分账户。
- 修复：允许进入兑换确认，由 `/api/redemptions` 检查实时积分及奖品库存。保留兑换确认和防重复提交，成功后刷新账户与兑换记录。
- 验证：页面缓存积分为零，服务器完成订单后，原页面可直接成功兑换；扣除积分数正确。真实积分不足时仍被后端拒绝，积分没有重复扣减。

## 二、影响客户端、但根因在共享层的问题

### S01：旧账号请求迟到的 401 会清除新账号登录态

- 优先级：P2；状态：待共享层维护者修复，当前尚未消除。
- 根因位置：`mobile/shared/api.js:162` 的 401 处理。
- 客户表现：切换账号后，新账号可能突然被要求重新登录。
- 复现：账号 A 的订单请求未返回；退出 A，登录 B；随后 A 的旧请求返回 401。共享层不区分请求所属令牌，直接清除当前 B 的令牌和用户，客户端再跳登录。
- 证据：使用原共享脚本在内存中控制响应顺序，B 登录后为 `token=B, user.id=2`，A 的迟到 401 返回后变为 `token='', user=null`。未访问或修改原数据库。
- 建议：请求发起时捕获令牌，只在收到 401 且该请求令牌仍等于当前令牌时清除登录态；增加 A/B 换号与迟到响应的回归测试。必要时返回可识别的 HTTP 状态给上层。
- 边界：本轮没有直接修改冻结共享层，也不应宣称客户登录问题已全部修复。普通 401 跳转、保留来路及普通错误不误跳的测试通过，不能覆盖或消除本项跨账号竞态。

## 三、整体项目：已复现的后端问题

### B01：整数参数校验会静默截断小数

- 优先级：P2；状态：待后端修复。
- 位置：`shop/auth.py:58` 的 `to_int`，内部执行 `int(value)`。
- 复现：登录后向 `/api/orders` 提交合法商品 ID 和 JSON 数字 `quantity: 1.5`。
- 实际：返回 HTTP 200，订单数量被写成 `1`。
- 预期：拒绝非整数数量，返回 HTTP 400，不创建订单。
- 验证：在临时数据库实测该请求并核对响应；随后取消测试订单。客户端本身已校验整数，但直接调用 API 可以绕过前端，因此后端仍需独立修复。
- 建议：整数校验前明确检查输入类型和数值，禁止静默截断小数；一并测试数量、价格、库存、余额调整等复用此工具的字段。是否允许整数形式字符串，应由后端统一约定。
